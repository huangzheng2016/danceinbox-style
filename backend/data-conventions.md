# Data Conventions (gorm/gen + IRedis)

Normative rules for ALL business code touching the database or the cache: `biz/service/**`, `biz/handler/**`, `biz/mw/**`. The first half governs the gorm/gen query layer, the second half the `IRedis` cache seam. These rules exist because every pattern on the forbidden list has caused a real bug.

## The one rule underneath everything

Business code ONLY talks to the typed DAO layer generated by gorm/gen:

```go
q := mysql.GetDBQuery().User
u, err := q.WithContext(ctx).Where(q.ID.Eq(id)).First()
```

Forbidden in business code (`biz/service`, `biz/handler`, `biz/mw`):

- `mysql.DB()` raw handle, `db.Model(...)`, `db.Table(...)`, `db.Raw(...)`, `db.Exec(...)`
- string conditions of any kind: `Where("col = ?", v)`, `Or("id = ?", x)`, `Order("u.id ASC")`, `Select("a, b, count(*)")`
- map-based `Updates(map[string]any{...})` — untyped column names

Raw gorm may exist ONLY inside `biz/dal/mysql/`: `init.go`, `migrate.go`, typed aggregate helpers in that package, and small constructor files that hand the raw handle to an external tool (e.g. `adapter_casbin.go` builds the Casbin gorm-adapter — see `auth-jwt-casbin.md`). The raw `*gorm.DB` never crosses the DAL boundary into services, handlers, or middleware. If a query genuinely cannot be expressed with typed field methods (GROUP BY aggregates, `DATE_FORMAT`, `DISTINCT`), it goes behind a typed function in `biz/dal/mysql/aggregate.go` that business code calls — never inline strings in a service.

## Conditions

Every condition is built from generated field methods — never strings, never hand-written SQL fragments:

- Equality / sets: `q.ID.Eq(id)`, `q.Status.Neq(s)`, `q.ID.In(ids...)`, `q.ID.NotIn(ids...)`
- Ranges: `.Gt` / `.Gte` / `.Lt` / `.Lte`, `.Between(a, b)`
- Null: `.IsNull()` / `.IsNotNull()`
- Pattern: `.Like(utils.LikeQueryStr(s))` — LIKE input MUST be escaped through it, never `"%" + s + "%"` (sole definition: `backend-skeleton.md` "utils/utils.go").

Combining:

- AND: chain `.Where(...)` calls, or pass multiple conditions to one call (`Where(a, b, c)`). Do NOT use `.And()` / `.Not()`.
- OR: rare. One nested form only: `q.Where(q.Where(A).Or(B))`.
- Booleans: model bool-ish columns as `int32` tinyint (or better, status enums). Compare with `.Eq(1)` / `.Eq(0)`. Never `.Is(...)` — there are no bool fields in this schema style.

## Reads

- Single row: `.First()`. Do not introduce `.Take()` / `.Last()`.
- Batch fetch by ids: `.Where(q.ID.In(ids...)).Find()` — this, not raw joins, is how "related rows" are loaded (the generated models declare no relations).
- Large `IN` sets must be chunked (roughly 500-1000 ids per query). A single query binding thousands of values can exceed the server's max query size or placeholder limit, and it fails as a runtime 500, not at compile time. This applies to every `In(ids...)` call whose input size is caller-controlled.
- Not-found: the SERVICE owns the translation. Inside the service, test `errors.Is(err, gorm.ErrRecordNotFound)` (never `err == gorm.ErrRecordNotFound`) and return the package sentinel instead — `var ErrNotFound = errors.New("not found")` declared once in `biz/service/<feature>/`. `gorm.ErrRecordNotFound` never crosses the service boundary: handlers and middleware test `errors.Is(err, user.ErrNotFound)` and map it to HTTP 404 with `consts.ErrNotFound` in the body code. (Two different `ErrNotFound` names, kept straight by package: the service sentinel is an `error`; `consts.ErrNotFound` is the int wire code.)
- Every chain starts with `.WithContext(ctx)` — including inside transactions and in background goroutines (re-derive a context there; do not drop it and do not silently use `context.Background()`).

## Pagination

List endpoints use `FindByPage(offset, limit)` only — never manual `.Offset()` / `.Limit()`. The IDL carries `page`/`page_size` (see `idl-workflow.md` "Canonical `base.thrift`"); the service converts first — `offset = (page - 1) * page_size`, `limit = page_size` — then clamps BOTH bounds via the helper that lives in `biz/dal/mysql/page.go`:

```go
// biz/dal/mysql/page.go
package mysql

func ClampList(offset, limit int) (int, int) {
    if offset < 0 {
        offset = 0
    }
    if limit <= 0 || limit > MaxLimit {
        limit = MaxLimit
    }
    return offset, limit
}
```

```go
offset, limit := mysql.ClampList((int(req.GetPage())-1)*int(req.GetPageSize()), int(req.GetPageSize()))
rows, total, err := q.FindByPage(offset, limit)
```

`page`/`page_size` are declared `optional i32` WITH defaults in the IDL, and thriftgo generates such a field as a plain VALUE field — `req.Page` is an `int32`, so `int(req.Page)` compiles fine. Only an optional field WITHOUT a default generates a pointer (`*int32`); there the generated getter's real job is nil-safe dereference. Either way, do not read the IDL-written `= 1` / `= 20` as effective: `BindAndValidate` never applies IDL-declared defaults, so when the client sends no `page`/`page_size` the fields hold the Go zero value and `req.GetPage()` returns `0`, not `1`. Those zeros flow straight into `ClampList`: `limit <= 0` clamps up to `MaxLimit = 50` (not the IDL's 20), and `page = 0` yields a non-positive offset the clamp floors to 0 — an omitted-everything request silently paginates as page 1, size 50. If the response echoes `page`/`page_size` back to the client, normalize them yourself first (`page = max(1, page)`, and echo the effective size after clamping), or you return `0`s for a request that actually served page 1. The nil-safety rule still stands for pointer-typed optionals elsewhere: always read them through the generated getters.

The one-sided `if req.GetPageSize() > MaxLimit { ... }` is a bug source (0 and negative sizes slip through). That is why the clamp helper is mandatory and two-sided.

Filtering or deduplicating AFTER `FindByPage` produces short pages (page size 20, client sees 14) and drifts the total away from what the rows add up to. Push the filter into the `Where` clause. If dedup is genuinely unavoidable (join fan-out duplicates), over-fetch and refill the page to the requested size before returning.

## Writes

### Create

`.Create(&model.X{...})`; bulk: `CreateInBatches(rows, 100)`.

### Update — picking the right form

There are exactly three update forms. Choose by what you need:

1. **Typed assign-expression update (the default).** Pass `field.AssignExpr` values; zero values (`0`, `""`, `false`) are written as given:

```go
_, err := q.WithContext(ctx).Where(q.ID.Eq(id)).
    UpdateSimple(q.Status.Value(0), q.Name.Value(name))
```

gen v0.3.x generates two variants of this method:

- `UpdateSimple(cols...)` — goes through gorm `Updates`: hooks run and gorm auto-writes `updated_at`. Never put `q.UpdatedAt.Value(...)` in the list yourself.
- `UpdateColumnSimple(cols...)` — goes through gorm `UpdateColumns`: skips hooks AND skips the automatic `updated_at` write. Use only when `updated_at` must stay untouched (e.g. pure counter/heartbeat bumps on a row whose `updated_at` carries business meaning).

Method names come from the gen version that generated `biz/dal/mysql/query/*.gen.go`. Before using either name, confirm it against the generated interface in that directory; if the generated DAO declares different names, the generated code wins — do not copy a name from this document into code that must compile.

2. **Struct patch update**: `.Updates(&model.X{Field: v})` — gorm struct semantics SKIP zero-value fields, so this form silently cannot write `0` / `""` / `false`. Use it only when skipping zeros is exactly what you want, or force columns with `.Select(q.Col1, q.Col2).Updates(&model.X{...})`. Prefer form 1 when in doubt.

3. **Atomic expression on one column**: `UpdateSimple(q.Coin.Add(n))` (negative `n` for decrement). Never read-modify-write a counter in Go.

### CAS — conditional update is the only state transition

Any update that depends on the row's current state (state machine transitions, balance checks, claim/lease handoff, optimistic locking) MUST put the precondition in `Where` and assert `RowsAffected`. This is the TOCTOU guard; a bare `First` then update is a race.

```go
res, err := u.WithContext(ctx).
    Where(u.ID.Eq(id), u.Coin.Gte(amount)).
    UpdateSimple(u.Coin.Add(-amount))
if err != nil {
    return err
}
if res.RowsAffected == 0 {
    return ErrInsufficientBalance
}
```

State transition:

```go
res, err := q.WithContext(ctx).
    Where(q.ID.Eq(id), q.Status.Eq(StatusPending)).
    UpdateSimple(q.Status.Value(StatusRunning))
if err != nil {
    return err
}
if res.RowsAffected == 0 {
    return ErrConflict // someone else transitioned it first
}
```

`RowsAffected == 0` means "precondition did not hold" — map it to a domain conflict error, never ignore it, never treat it as success.

`ErrConflict`, `ErrInsufficientBalance`, and `ErrConcurrentModification` are SERVICE-PACKAGE sentinel errors, declared once in the owning `biz/service/<feature>/` package as `var ErrConflict = errors.New("conflict")` — the same pattern as `ErrNotFound` in "Reads". Handlers test them with `errors.Is(err, service.ErrConflict)` and map to HTTP 409 with `consts.ErrConflict` in the body code. Two different `ErrConflict` names, kept straight by package: the service sentinel is an `error`; `consts.ErrConflict` is the int wire code (1005, see `backend-skeleton.md` "biz/consts/errcode.go"). Domain sentinels never enter `consts`, and the numeric code never appears in service code.

### Version columns — optimistic locking

Tables with a `version int` column do read-modify-write by folding the version into the CAS:

```go
res, err := q.WithContext(ctx).
    Where(q.ID.Eq(id), q.Version.Eq(old.Version)).
    UpdateSimple(
        q.Version.Value(old.Version+1),
        q.Name.Value(newName),
    )
if err != nil {
    return err
}
if res.RowsAffected == 0 {
    return ErrConcurrentModification
}
```

Rules:

- The version was read earlier (by the same request or supplied by the client); the update carries it in `Where` and increments it in the same statement. `updated_at` is NOT a version column — do not compare timestamps for concurrency control.
- Every writer of a versioned table bumps `version` on every content change; a writer that forgets the increment silently defeats everyone else's CAS.
- On `RowsAffected == 0`, either surface a conflict error or re-read and retry the whole read-modify-write cycle (bounded retries) — never retry the bare update with the same stale version.
- If the model has no version column and you did not add one, the plain CAS forms above (status / balance precondition in `Where`) are the concurrency mechanism. Do not invent per-request ad-hoc locking instead.

### Upsert

Generated `.Save(&x)` (OnConflict update-all) or an explicit transaction + `First`/`Create`. No ad-hoc read-then-write upserts outside a transaction.

## Deletes

Soft delete is one of two schemes. Pick ONE per table, at model design time; do not mix schemes across tables that reference each other, and do not invent a third.

**Scheme A — status / `is_delete` column.** "Delete" is a typed update (`UpdateSimple(q.IsDelete.Value(1))` or a status transition); every list query adds `.Where(q.IsDelete.Eq(0))` explicitly. Choose this when the row already has a lifecycle state machine, or when the deployment database cannot express the partial unique indexes Scheme B needs. Unique indexes are unaffected, but nothing filters deleted rows for you — forgetting the predicate is the classic bug of this scheme.

**Scheme B — `gorm.DeletedAt`.** The model carries `DeletedAt gorm.DeletedAt \`gorm:"index"\``. gorm/gen then auto-filters deleted rows on every query and `.Delete()` writes the timestamp instead of removing the row. Rules:

- Unique indexes on user-visible columns (name, slug) must be partial (`uniqueIndex:...,where:deleted_at IS NULL`) or include `deleted_at` in the key — otherwise a deleted row blocks re-creating the same name.
- `.Unscoped()` is forbidden in business code. Admin purge / restore lives behind a dedicated function in `biz/dal/mysql/`, not inline in a service.
- Targeted `ON CONFLICT` upserts on these tables must add the same `deleted_at IS NULL` predicate to the conflict target.

Hard `.Delete()` (row actually removed) is allowed ONLY on link/assoc tables, and always with a `Where`. Never `.Unscoped()` in business code regardless of scheme.

Delete semantics at the service boundary:

- Deleting an already-absent row is a SUCCESS (report `deleted=false` or treat `RowsAffected == 0` as an idempotent no-op), not an error. Retries and double-clicks must be safe.
- A delete that is only legal in certain row states (only `pending`, only owned-by-caller) puts the state in `Where` as a CAS; `RowsAffected == 0` on an EXISTING row maps to the domain conflict error, never a silent no-op and never a forced delete.
- Rows that carry an audit trail (decided by, decided at, reviewer notes) are never physically deleted once decided; see `auth-jwt-casbin.md` "Authorization Rules Beyond Middleware".

## Transactions

Exactly one form. Inside the closure use ONLY `tx.*` DAOs — never the singleton:

```go
txErr := mysql.GetDBQuery().Transaction(func(tx *query.Query) error {
    if err := tx.ChallengeSubmit.WithContext(ctx).Create(submit); err != nil {
        return err
    }
    u := tx.User
    _, err := u.WithContext(ctx).Where(u.ID.Eq(userID)).
        UpdateSimple(u.Score.Add(score))
    return err
})
```

CAS rules apply inside transactions too: a precondition in `Where` plus a `RowsAffected` check, returning a domain error from the closure to roll back.

## Caching (IRedis)

The rules below govern call sites using the `IRedis` seam (`biz/extension/redis`) as a cache, and the concurrency patterns that come with it. The seam mechanics (interface, providers, lock contract, pub/sub contract) live in `backend-skeleton.md` for the full profile and `lite-profile.md` for `LocalRedis`.

## What May Be Cached

Cache a read only when ALL of these hold:

- The result is expensive to produce (slow backend, heavy aggregate, remote call) AND reads outnumber writes.
- A bounded staleness is acceptable. A TTL-only cache has a staleness window up to its TTL; state that bound at the call site. If a write must be visible on the very next read, invalidate on write or do not cache that read at all. Do not shorten TTLs to paper over a missing invalidation path.
- The result is a CLOSED fact. Never cache an open window: in-progress counters, "today" aggregates, partial time ranges, anything still accepting writes. Split large ranges into aligned sub-windows (per day, per hour) so the closed prefix is cacheable and only the open tail bypasses the cache. Caching an open window is how a frozen stale count ships to users.

## What May NOT Be Cached

- Errors. A cached error poisons the key until expiry: a backend that was briefly down stays down for every caller, and a cold cache that can never fill keeps re-hammering the backend it was meant to protect. On load failure, return the error and write nothing.
- Misses (not-found / empty results), unless the miss itself is the expensive fact and gets its own deliberate short TTL. Default: do not cache misses.

## Cache Miss vs Backend Errors

Both profiles expose the same `biz/extension/redis.ErrCacheMiss` sentinel. The full adapter maps go-redis's `redis.Nil` to it; `LocalRedis` returns it directly. Business code uses `errors.Is(err, redis.ErrCacheMiss)` through the project's extension package and never imports `goredis` or compares error strings.

Only `ErrCacheMiss` means the key is absent. Other errors mean the cache backend failed. An ordinary cache read MAY deliberately degrade to the backend load, but it must log the cache error and still satisfy the singleflight and cancellation rules below. Permission, quota, and other fail-closed guardrails MUST return the error instead of treating it as a miss.

Every ordinary cached read path must still work with the cache unavailable. That is an explicit degradation decision, not a reason to erase the distinction between absence and outage.

## Singleflight (the Once pattern)

Every cached read of a slow backend goes through a per-key singleflight: N concurrent misses for the same key produce exactly ONE backend load, and the other callers wait and share the result. Use `go-redis/cache`'s `Once`, or `golang.org/x/sync/singleflight` behind the seam.

Placement rule: `go-redis/cache` wraps a go-redis client, so its `Once` — and any singleflight implementation that touches the concrete client — lives ONLY inside `biz/extension/redis` (full profile), exposed as a seam method. Business code (`biz/service`, `biz/handler`, `biz/mw`) never imports `goredis` or `go-redis/cache`; it calls the seam (the same boundary as "Cache Miss vs Backend Errors").

- Short TTLs (tens of seconds to a few minutes) are the norm for singleflight caches. The goal is collapsing concurrent cold reads and absorbing refresh bursts, not long-term storage.
- The load function AND the cache write must survive caller cancellation: run them with `context.WithoutCancel(ctx)` or a detached context with its own timeout. A fill driven by the request context dies when the client disconnects, so the cache never warms and every request re-hammers the backend.
- When the fill is expensive relative to request latency, decouple it from the request entirely: serve the stale or empty value and fill in the background.

## Cache Keys

- One canonical key builder per cached read path. Canonicalize before hashing: sort list-valued parameters, trim and normalize case on search strings. Two equivalent requests that differ only in parameter order must hit the same key.
- Carry a version segment in the key (`v2:`) and bump it when the payload shape changes; old-shape entries expire on their own.
- Delete keys the code no longer produces or consumes. A dead key is not harmless: it hides staleness bugs and wastes memory. When a cached read path is removed, its key space is deleted in the same change.

## TTL Discipline

One TTL policy per read path, named as a constant. Do not scatter ad-hoc TTL literals across call sites.

## Concurrency Rules Beyond CAS

The DB-side rules (CAS, version columns, transaction form) live in "Writes" and "Transactions" above; the lock and pub/sub contracts live in `backend-skeleton.md`. The rules below cover the rest.

- **Lock ordering**: when a critical section takes more than one lock, or locks more than one row inside a transaction, acquire them in one fixed global order everywhere (for example sorted by id). Two code paths that lock the same set in different orders are a deadlock waiting for the right interleaving.
- **Not-found on cancel/delete is usually success**: when canceling or deleting through a downstream system returns not-found, the effect has usually already happened. Treat it as success, finish the idempotent terminal write, and move on - never retry it as a failure.
- **Fail-closed guardrails**: when a protection read fails (quota check, ruleset snapshot, permission lookup), the operation fails too. Proceeding on a lenient or stale fallback turns every guardrail outage into an unrestricted window.
